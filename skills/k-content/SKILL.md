# /k-content — words in the project's voice

> **Project settings first:** if the project's `AGENTS.md` has `## Skill settings` → `### /k-content`, read it and apply it on top of this skill. Settings add steps or tighten rules; they never loosen the kit's Safety rules.

1. **Voice.** Read the project's voice file (`AGENTS.md` names it; usually `docs/brand/voice.md`). If there is none, draft one first (audience, tone, words to use and avoid, 2–3 good examples from the product) and ask the user to confirm it — then save it for next time.
2. **Brief.** Be clear on: where the text appears, who reads it, the one thing it must achieve, length limits (button, headline, meta description…), language(s).
3. **Facts.** Only claims the product really supports — check the feature exists. No invented numbers, testimonials or customer names.
4. **Write 2–3 options** that differ in approach (e.g. benefit-led vs. problem-led vs. plain), not just wording. Mark the one you recommend and why.
5. **Check each option:** fits the length, reads aloud naturally, no jargon the audience would not use, consistent terms with the rest of the product (grep existing UI text for the terms).
6. **After the user picks:** put it in place (the right component, translation file or page), keep the same term everywhere it appears, and ship via the normal flow. New recurring terms or phrases go into the voice file.
